# Spec-First Workflow

## Overview

코드와 같은 위치(co-located)에 스펙 문서를 두어, 코드 작업 시 AI가 도메인 컨텍스트를 자동으로 확보하게 하는 워크플로우. EVUI 는 `src/components/<컴포넌트>/SPEC.md` · `DECISIONS.md` 로 컴포넌트 도메인마다 co-located 하고, 공통 규약은 `src/components/SPEC.md`, 공용 유틸은 `src/common/SPEC.md` 에 둔다.

이 스킬은 두 경로로 진입한다:

- **직접**: 사용자가 SPEC/DECISIONS 문서를 명시적으로 다루도록 요청한 경우.
- **서브스텝**: 코드 작업/리뷰의 "작업 전 SPEC 탐색" 단계에서 이 절차를 따르는 경우. 이때는 **탐색을 가볍게** 유지하고 원래 작업 흐름으로 결과를 돌려준다.

> **이 스킬이 EVUI SPEC 워크플로우의 단일 진실의 원천(SSOT)이다.** 프로젝트 `CLAUDE.md` 의 "Spec Workflow" 섹션은 이 스킬을 가리키는 얇은 포인터다.

필요할 때만 읽는 참조 문서:

| 문서 | 읽는 시점 |
|------|-----------|
| `references/authoring.md` | SPEC/DECISIONS **본문을 쓰거나 고칠 때** (생성·갱신 공통) — 섹션 구성, 코드 대조 검증, 분할 규칙 |
| `references/compliance.md` | 코드 **리뷰**에서 SPEC 준수를 판정할 때 — 위반 심각도, 체크리스트 |

위 조건에 해당할 때만 연다 — 1·2단계(탐색·반영)만 하는 경우에는 둘 다 필요 없다.

## Workflow

### 1. 스펙 탐색 (작업 전)

```
1. 작업 요청 분석 → 영향받는 파일/폴더 파악
2. 영향 범위 내 SPEC.md 탐색 (하위가 상위보다 우선)
3. DECISIONS.md 탐색 (SPEC.md와 같은 폴더)
4. SPEC.md가 없는 경우 → 생성 제안
```

**탐색 방법** — 변경 대상 디렉토리에서 레포 루트 방향으로 ↑ 올라가며 Glob 으로 `SPEC.md`·`DECISIONS.md` 존재를 확인한다(`<target-dir>` → 부모 → 조부모 → `<repo-root>`). 도메인 컨텍스트는 상위에, 구체적 룰은 하위에 있으므로 **가장 가까운 것이 우선**한다.

**토큰 가드** — 매칭된 SPEC.md 가 5개를 초과하면, 변경 파일 디렉토리 기준 가장 가까운 3개만 Read 하고 나머지는 "+N개 SPEC 더 발견됨"으로 보고에 명시한다.

**DECISIONS.md 조건부 읽기:**

- 코드 수정 / 새 기능 추가 / 설계 변경 → SPEC.md + DECISIONS.md **모두** 읽기 (설계 충돌 감지에 필수)
- 단순 구조 파악 / 버그 수정 / 스타일 변경 → SPEC.md만 읽기 (DECISIONS.md는 필요 시)

**SPEC.md가 없는 경우** — 사용자에게 생성 여부를 묻는다("이 폴더에 SPEC.md가 없습니다. 생성할까요?"). "네"면 코드 작업 전에 현재 코드를 분석해 초안을 쓰고 작업 컨텍스트로 활용한다. 단, 다른 작업 흐름의 서브스텝으로 진입한 경우에는 흐름을 끊지 않도록 생성 제안만 보고에 남기고 강제로 멈추지 않는다.

### 2. 스펙 반영 (작업 중)

SPEC.md의 각 섹션을 코드 작업에 적극 활용한다:

- **Business Rules**: 규칙/제약이 코드에 정확히 반영됐는지 확인. 예: "비로그인 사용자는 비공개 항목을 볼 수 없다" → 해당 가드가 코드에 있는지 검증
- **Dependencies**: import/호출 관계가 SPEC.md에 명시된 의존성과 일치하는지 확인. 새 의존성 추가 시 SPEC.md 업데이트 대상으로 메모
- **Architecture / File Structure**: 새 파일/컴포넌트 추가 시 기존 구조 패턴을 따름
- **Glossary**: 도메인 용어를 코드(변수명·함수명)에 일관되게 사용
- **DECISIONS.md**: 설계 결정의 이유를 이해하고, 그에 반하는 변경을 하려면 사용자와 먼저 논의. 날짜를 통해 오래된 결정이 현재 상황에 맞는지 재검토를 고려한다.

### 3. 스펙 업데이트 (작업 후)

**갱신 판단 원칙** — SPEC 은 **관찰 가능한 계약**(이 도메인이 밖에 무엇을 보장하는가)을 기술한다. 계약이 바뀌면 갱신하고, 계약 뒤편의 구현만 바뀌면 갱신하지 않는다. 갱신 대상이면 사용자에게 제안한다:

```
"기능이 변경되었어요. SPEC.md 업데이트할까요?"
```

**갱신 불필요** — 계약이 그대로면 SPEC 을 건드리지 않는다. 아래는 원칙에서 자동으로 도출되지 않으므로 명시한다:

- 내부 구현 리팩토링
- 버그 수정 (명세 변경 없음)
- UI/스타일 변경
- 성능 최적화

**DECISIONS.md** — 갱신 대상에 해당하는 변경이면 SPEC.md 갱신과 함께 같은 폴더 DECISIONS.md 에 행을 추가한다:

| 날짜 | 결정 | 이유 | 대안 |
|------|------|------|------|
| YYYY-MM-DD | 변경 내용 요약 | 왜 이렇게 결정했는지 | 검토했지만 채택하지 않은 방안 |

**수동 트리거** — "스펙 업데이트 확인해줘" 요청 시 현재 코드와 SPEC.md를 비교 분석한다.

> SPEC/DECISIONS **본문을 쓰거나 고칠 때**(신규 생성 포함)는 `references/authoring.md` 의 섹션 구성과 코드 대조 검증 절차를 따른다. 새 파일은 `assets/SPEC.template.md`·`assets/DECISIONS.template.md` 두 개를 함께 만든다.
